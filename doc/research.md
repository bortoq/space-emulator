# Исследование: `NONE`, механизм загрузки и «первый read из `SYS`»

Дата: 2026-10-17. Роль: Algorithmist/Researcher. Вопрос: что такое
`NONE`; как идёт загрузка при единственной инструкции и без каналов
данных; решает ли предложение «читать загрузочный код первым `read` из
`SYS`» нерешённый пункт.

## 1. Что такое `NONE`

`op = 0` — служебное значение «пусто / нет операции». Задано в
`proto.def` (`XOP(NONE, 0)`, комментарий «0 = NONE/empty»), в коде —
`sys_ctrl.c:305` (`case OP_NONE: break;`) и `rsp_reset`
(`sys_ctrl.c:173`).

- Никакого действия не выполняет: `service()` для `NONE` выходит, записав
  в ответ `op = NONE`, остальные поля нулевые.
- Нужен, чтобы **занулённая запись была корректной**: неинициализированная
  или уже прочитанная запись не должна запускать случайную операцию.
- Служит маркером «нет текущей операции» в ответе (и «нет запроса» в
  записи).

То есть `NONE` — это не действие канала, а **отсутствие действия**.
Любое другое значение `op` — реальная операция.

## 2. Как загрузка устроена сейчас

Загрузка **не является операцией канала** и не требует открытых каналов.

- `init_space` (`engine.c:625-630`) записывает в слот 0 загрузочную
  инструкцию: `n = proc_n * instruction_size`, `dst = PROCESSOR_START`,
  и ставит `boot_pending`.
- В первом такте `run_instruction(0)` (`engine.c:516-522`) при
  `boot_pending` вызывает `space_input(n + status_bits, 0, stdin)`: читает
  `proc_n * instruction_size` бит **из stdin** прямо в
  `[0, proc_n*instruction_size)` и дописывает запись статуса. Если бит
  меньше — процессор заполняется NOP и пространство останавливается.

Следствия:

- «никаких данных» — неверно: данные есть, это биты программы на stdin
  (`proc_n * instruction_size` бит).
- каналы не нужны: ни `SYS`, ни данные. Загрузка — **хостовый примитив**.
- это работает и в минимальном пространстве `-s 27 -p 1`: загрузчик —
  одна 14-битная инструкция, читающая 14 бит; но тогда вся загружаемая
  программа — тоже одна инструкция (места под драйвер нет; см. §12.4
  роадмапа).

## 3. Эталон `copy-space`

Там ровно та же идея уже реализована: `src/core.c` содержит маленький
**встроенный загрузчик** (4 инструкции, `core[]`), который читает поток
через канал и раскладывает образ; `core_init()` засевает этот образ, а
`core_load_file()` — сырой дамп (`--core`). То есть «загрузочный код,
читаемый через канал» — уже существующий паттерн, а не новшество.

## 4. Предложение: читать загрузочный код первым `read` из `SYS`

Идея: `SYS` выступает как «boot ROM» — первое `read` из `SYS` отдаёт
код инициализации (установщик механизмов, включая драйвер каналов).

Оценка:

- **Да, это корректно и реализуемо**; это обобщение паттерна `copy-space`
  на `SYS`.
- **Нет, это НЕ решает открытый пункт §4 vs §7** (где инициируется
  операция данных: запись `{op=READ/WRITE, ptr, len}` через `SYS` или
  прямо в канал данных). Это ортогональный вопрос.
- **Что оно действительно решает:** как попадает начальный код/драйвер,
  когда каналов данных ещё нет. Сейчас это решает хостовый boot из stdin;
  предложение даёт этому определённую роль (первое чтение) и убирает
  хостовую особость.
- **Цена:** `SYS` перестаёт быть «каналом без данных» — как минимум один
  раз он отдаёт образ. Нужна явная оговорка-исключение либо маршрутизация
  образа через канал данных (§ варианты ниже).

## 5. Варианты

### Вариант A. Оставить хостовый boot (stdin), без ROM

| Критерий | Оценка |
|----------|--------|
| Сложность | 0 (базовый) |
| Риски | нет новых; загрузчик+драйвер должны уместиться в `proc_n` |
| Плюсы | уже работает; `SYS` чист; минимальные изменения |
| Минусы | загрузка — хостовый примитив, не выражается через каналы; два механизма (boot + каналы) сосуществуют |

### Вариант B. `SYS` как boot ROM (первое `read` из `SYS`)

| Критерий | Оценка |
|----------|--------|
| Сложность | 2–4 дня |
| Риски | ломает инвариант «данные не через `SYS`»; нужны протокол/версия/хэш ROM; эмулятор начинает поставлять код в пространство; размер ROM и его доставка |
| Плюсы | единый механизм входа; `SYS` доступен даже после разрушения пространства (частичный «last resort»); совпадает с духом `copy-space` |
| Минусы | «дырка» в модели SYS; сложнее версионирование; boot-путь становится частью протокола |

### Вариант C. Двухстадийно: хостовый boot + образ через канал данных

| Критерий | Оценка |
|----------|--------|
| Сложность | 1–2 дня |
| Риски | нужен хост-конвенции device (например, `dev=N` = образ); взаимодействие с уже открытыми каналами |
| Плюсы | сохраняет модель «данные — только через канал данных»; `SYS` чист; использует уже существующий `OPEN`/`READ` |
| Минусы | две стадии; маленький хостовый загрузчик всё равно нужен; канал под образ нужно открыть до кода, который его обслуживает |

## 6. Вывод

- `NONE` — это «нет операции» (нулевое значение), а не действие.
- Загрузка сейчас идёт **через stdin (хост)**, а не через каналы; данные
  при загрузке есть (биты программы), каналы не нужны.
- Предложение читать загрузочный код первым `read` из `SYS`
  **реализуемо** и соответствует паттерну `copy-space`, но решает только
  задачу «как попадает начальный код/драйвер». Открытый пункт «где
  инициируются операции данных» оно не закрывает и добавляет новое
  решение: допустим ли образ в `SYS`.

Рекомендация к обсуждению: выбрать между B (единый вход через `SYS`,
с явным исключением в модели) и C (сохранить модель, образ — через канал
данных). Вариант A — если единый механизм входа не требуется.

## 7. Зафиксированные решения по обсуждению (boot, каналы, `dev`)

Дополнение от 2026-10-17 (по обсуждению с заказчиком).

1. **Копирование канала данных = только данные.** `dst = канал` — запись
   данных, `src = канал` — чтение данных, `n` бит. Никаких записей и
   статуса в канале. (Исправлено: `sys_ctrl.c` переписан, канал данных
   носит только данные.)
2. **Всё управление — только через `SYS`:** `CLOSE`/`SEEK`/`FSTAT`/
   `IOCTL`, статус, в будущем `SPAWN` (`OPEN` убран — открывать нечего).
3. **`READ`/`WRITE` как опкоды не нужны** — чтение/запись есть копирование
   через канал.
4. **Каналы старта пред-открыты** (как в старом `DATA`, где stdin/stdout
   были совмещены в один канал): эмулятор на старте инициализирует массив
   каналов уже открытыми fd 0/1. Открытый вопрос: один общий stdio-канал
   или два (`stdin`/`stdout`).
5. **`dev` при фиксированной привязке по позиции не нужен** (привязка
   `позиция ↔ fd`). Возможное исключение — динамические устройства;
   тогда `dev` остаётся только для них.
6. **Seed (сид)** — первая инструкция, читающая загрузочный образ из
   канала stdin в процессор (`PROCESSOR_START`); это обычная копия, без
   специального смысла. Термин «boot instruction» заменяется на «seed».
7. **Кадрирование — не забота эмулятора.** Эмулятор отдаёт байты потока;
   загрузчик в образе знает свой размер и дочитывает себя сам.

## 8. Подтверждено заказчиком (2026-10-17)

1. **`dev` — удаляем.** Привязка каналов к устройствам **по позиции**.
   Копикод сам позиционирует файл в канале (SEEK через `SYS`) и сам
   следит за позицией.
2. **`READ`/`WRITE` — убираем** из `SYS`: чтение/запись = копирование
   через канал.
3. **Два канала:** `stdin` и `stdout` раздельно, пред-открыты на старте.
4. **Seed** — обычная копия (`(размер_образа, PROCESSOR_START, позиция
   stdin-канала)`), без спец-смысла.

### Производные следствия (подтверждены заказчиком)

- **`OPEN` исчезает, `CLOSE` остаётся.** При фиксированном наборе
  устройств открывать нечего; `CLOSE` нужен, чтобы закрыть сам `SYS`.
- **`SYS` — обычный канал** (entry 0, позиция `space_nbits`) и его можно
  закрыть. После закрытия `SYS` пространство изолировано от хоста:
  управлять каналами и читать их состояние больше нельзя.
- **Состояние операции читается через `FSTAT`** (расширен): возвращает
  `size` и `moved`/`eof`/`status` последней операции данных. Отдельной
  операции не вводим.
- **Множество операций `SYS`:** `NONE`/`CLOSE`/`SEEK`/`FSTAT`/`IOCTL`
  (+ будущий `SPAWN`).
- **Запись-запрос `SYS`** ссылается на канал **позицией** (`chan`, `ADDR`).
  Ширина: `op(8) + chan(ADDR) + flags(16) + arg(32) + off(64)`; ответ:
  `op(8) + status(8) + flags(16) + size(64) + moved(NF) + eof(1)`.
- **Гранулярность копий данных:** байтовая (копикод выравнивает); для
  копии `n` бит копируется `ceil(n/8)` байт.

Реализовано в `proto.def`, `sys_ctrl.c`, `engine.c` (seed),
`tools/driver_gen.py`, тестах.
